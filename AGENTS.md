# AGENTS.md — reviewer-lottery

GitHub Action that lottery-assigns PR reviewers from `.github/reviewer-lottery.yml`. Core flow: `src/main.ts` builds PR info from the Actions context → `Lottery` (`src/lottery.ts`) orchestrates → `ReviewerSelector` (`src/core/reviewer-selector.ts`) picks → `GitHubServiceImpl` (`src/github-service.ts`) reads/writes the GitHub API.

No target-local `docs/*.md` (no `docs/` directory exists). Everything load-bearing is inline below. Config syntax, worked scenarios, and onboarding docs live in `README.md`; runnable config samples in `examples/*.yml`.

## Stack & Layout

- TypeScript, bundled by `tsup` to CJS, run as a `node20` GitHub Action.
- **Read-only committed build artifacts** (git-tracked, regenerated by `pnpm pack`): `dist/index.js` (minified, from `src/main.ts` — the action runtime that `action.yml` loads) and `bin/config-test.js` (non-minified, from `src/config-test.ts` — the config-test CLI). Never hand-edit; edit the `src/` source and rebuild.
- Selection logic lives in `src/core/reviewer-selector.ts`; config parse/validate in `src/config.ts`; API in `src/github-service.ts`.

## Commands

- `pnpm all` = `typecheck → format → lint → pack → test`, and CI (`.github/workflows/build.yml`) runs exactly `pnpm run all`. Note `format` is `biome format --write` (it **mutates** files), not `format-check`; `pack` rebuilds both artifacts.
- `pnpm config-test [path]` runs the local config tester (`bin/config-test.js`). Remote: `npx github:fan-k-tamura/reviewer-lottery config-test`.
- Single test: `pnpm test -- --testNamePattern="..."`.

## Build & committed artifacts (CONSTRAINT)

- **After any `src/` change you MUST rebuild AND commit both `dist/index.js` and `bin/config-test.js`.** `pnpm run all` runs `pack` but **never diffs the rebuilt bundle against the committed one**, so a stale `dist/index.js` passes CI green and the action/CLI silently ships old code.
- `tsup.config.ts` builds two CJS bundles, both `target: node20`, both with all deps inlined (`noExternal: [/.*/]`). Output must stay **CJS** even though `@actions/core` v3, `@actions/github` v9, and `chalk` v5 are ESM-only.
- Biome format/lint **excludes** `bin/**`, `dist/**`, `lib/**`, `node_modules/**`, `coverage/**`, and `**/*.min.js` (see `biome.json`) — the committed artifacts are deliberately not linted or formatted.

## Toolchain & supply chain (CONSTRAINT)

- **Install/rebuild with pnpm major 10.** CI pins `pnpm/action-setup` to version `10` (source of truth: `.github/workflows/build.yml`), while `mise.toml` pins `pnpm = "latest"` (installs 11+) — these conflict, so locally use `npx pnpm@10 install` / `npx pnpm@10 run all`. **Why (doc-sourced; the pnpm-side mechanism is external, not code-verifiable here):** the security-audit override pins in `package.json`'s `pnpm.overrides` block (see there for the current set) still aren't migrated to `pnpm-workspace.yaml`. Neither pnpm 10 nor 11 reads `pnpm.overrides` from `package.json` anymore (both warn), **but pnpm 11 additionally rewrites `pnpm-lock.yaml` to drop the `overrides:` section and re-resolves without it**, letting unpinned/vulnerable transitive versions back into `node_modules` (and into a rebuilt `dist` bundle); pnpm 10 leaves an up-to-date lockfile alone.
- **Node is constrained to `>=20.0.0 <21.0.0`** (`package.json` `engines`) and `.npmrc` sets `engine-strict=true`, so installs on Node 21+ **hard-fail**. The action runtime is `node20`.
- `.npmrc` also sets `minimum-release-age=7d`: installing/resolving any package version published **less than 7 days ago is refused** — adding or bumping a dependency to a fresh release fails until it ages 7 days.

## Reviewer selection logic

`ReviewerSelector.determineApplicableRule` picks ONE rule by strict priority, evaluated in this order, first match wins and **short-circuits** (a matching `by_label` rule returns early and fully overrides any author-group rule):

1. `by_label` (highest) 2. `by_author_group` 3. `non_group_members` 4. `default`.

- **Label matching** is case-insensitive and trims whitespace on **both** the PR label and the config label. Config load additionally **rejects duplicate `by_label` labels that collide after case-insensitive/trim normalization** (`src/config.ts`).
- **Multiple matching `by_label` rules** merge their `from`-clauses taking the **MAXIMUM count per target group** (not summed); rule type becomes `merged_labels`.
- **`when_author_in_multiple_groups`** defaults to `"merge"`: merges each author-group's `by_author_group` `from`-clause taking **max per target group** (type `merged_groups`). `"first"` uses only the first-listed group's rule. Only `"merge"`/`"first"` pass validation — **any other value throws** (`src/config.ts`). Merge-strategy nuance (`mergeRulesFromGroups`): an author-group with **no** matching `by_author_group` rule contributes `rules.default.from` into the per-target max-merge, and if `by_author_group` is entirely absent, merge returns `rules.default.from` directly — so a multi-group author's merged rule can be **inflated by the default rule** for each rule-less group they belong to.

### From-clause execution (`executeSelection`, `src/core/reviewer-selector.ts`)

Iterates `Object.entries(fromClause)` in **insertion order**; each step's picks are appended to `selected`. Per key:

- **`count <= 0` is skipped entirely** (`if (count <= 0) continue`). **PITFALL:** `"!group": 0` is therefore **INERT — it does NOT act as an exclusion.** Config validation rejects negative counts but allows `0`. Real exclusion needs a **positive** count on the `"!group"` selector. Concretely, pairing `"*": 1` with `"!ops,security": 0` does nothing to exclude — the `:0` is inert and `"*": 1` still assigns ops/security reviewers. To actually exclude a group, drop the `"*"` entry and give the `"!ops,security"` selector a **positive** count (as README's exclusion examples do).
- **Existing-reviewer subtraction is PER-GROUP, not global:** `remainingNeeded = max(0, count - existingFromGroups.length)`, where `existingFromGroups` is the existing reviewers that are candidates of **that** group key. Existing reviewers only reduce the requirement of groups they belong to.
- **Overlapping membership, existing reviewers (PITFALL):** because `existingFromGroups` is recomputed per group key, a **single existing reviewer counts toward EVERY** from-clause group whose candidate list contains them — one reviewer can satisfy multiple group quotas at once. Existing reviewers are **never consumed**.
- **Overlapping membership, newly-selected reviewers (asymmetric with the above):** the pick pool ignores `selected.concat(author, ...existingReviewers)`, so newly-selected reviewers ARE consumed **globally** across later from-clause steps in insertion order — the earlier-listed group claims a shared/overlapping member first. So the from-clause key **order is significant**. This also guarantees the author is never self-assigned and no reviewer is picked twice.
- **`pickRandom` gracefully UNDERFILLS:** loop guard is `while (picks.length < n && candidates.length > 0)` over a Set-deduped, ignore-filtered pool, so when the eligible pool is smaller than `remainingNeeded` it returns **fewer than requested** without throwing or looping (this is the fix behind the "prevent infinite loop in pickRandom when candidates insufficient" commit). The action therefore silently assigns fewer reviewers than a `from` count when the pool is exhausted.

### Randomness

Production selection uses `pickRandom` — `crypto.getRandomValues` with **rejection sampling** to eliminate modulo bias. `pickRandomDeterministic` is a seeded LCG **for deterministic tests ONLY** — do not wire it into the real selection path.

## Config validation (`src/config.ts`)

- `getConfig` does **NOT** hard-stop on a validation error: it catches, calls `core.setFailed`, and **RETURNS `{ groups: [] }`**. So `run()` continues with an empty config — the action is marked failed but still executes to the "no reviewers selected" path.
- `validateConfig` requires `selection_rules` to exist. From-clause validation: rejects **negative** counts (0 is allowed); requires every non-special group key to exist in `groups`; for `"!a,b"` exclusion keys, requires **each** comma-separated excluded group to exist. **Only `"*"` and keys starting with `"!"` bypass the group-existence check.**
- **The config-test CLI has its OWN, far WEAKER validator** (`ConfigTester.validateConfig`): it only checks that `groups` is an array, `selection_rules` exists, and each group has a name + usernames array, then emits advisory **warnings** for duplicate-selection patterns. It does NOT enforce non-negative counts, group-existence, duplicate-label normalization, or the `when_author_in_multiple_groups` value. So `pnpm config-test` can green-light a config the live action would **reject with a thrown error**.

## Existing reviewers & GitHub API

- **`GitHubServiceImpl.getExistingReviewers` MUST union `listRequestedReviewers` with paginated `listReviews` filtered to `COUNTED_REVIEW_STATES` = { APPROVED, CHANGES_REQUESTED, DISMISSED, COMMENTED }.** Why: GitHub drops a reviewer from `requested_reviewers` once they submit **any** review (including comment-only), so a requested-only implementation re-picks past reviewers (incl. stale-dismissed after rebase, or commenters dropped from the pending list). **`COMMENTED` is intentionally in the set on the same basis as `DISMISSED` — do not remove it** (it is the "treat commented-only reviews as existing reviewers" fix); a comment-only reviewer is excluded from the lottery just like APPROVED/CHANGES_REQUESTED.
- **Asymmetry in the `Promise.allSettled`:** if `listRequestedReviewers` rejects it **throws**; if only `listReviews` rejects it **degrades to requested-only** (keeps the successful requested call) rather than discarding it.
- **`Lottery.getExistingReviewers` swallows ALL errors from the service**, logs a warning, and returns `[]` (PITFALL): on any transient API failure the existing-reviewers set becomes empty, re-eligibling already-assigned/past reviewers for re-selection.
- **`Lottery.getExistingReviewers` is NOT cached** and is re-invoked at selection time and **again** inside whichever summary runs (`addSuccessSummary` / `addNoReviewersSummary`) — **2 full API round-trips per run** (each = `listRequestedReviewers` + paginated `listReviews`). This is asymmetric with `getPRAuthor`, which caches on `this.pr` after the first fetch. Combined with the swallow-to-`[]` behavior, the job summary can report a **different** existing-reviewer set than the one used for selection.

## Event context & runtime behavior (`src/main.ts`)

- **`by_label` rules only fire on `pull_request` / `pull_request_target` events (PITFALL).** The non-PR fallback branch of `extractPRInfoFromContext` (reads `GITHUB_REF`) returns **no labels**, so label-based selection silently never applies on manual/other triggers. For label rules to re-run when a label is added, the workflow must trigger on `pull_request` with the `labeled` activity type (e.g. `types: [opened, synchronize, reopened, labeled]`).
- **PR-author resolution precedence:** `prInfo.author = payload.pull_request.user.login || core.getInput("pr-author") || undefined` (payload **wins** over the input on PR events). `Lottery.getPRAuthor` returns `prInfo.author` directly with **no API call** when present; only when absent does it fetch via `githubService.getPRAuthor` (`pulls.get` → `data.user.login`) and cache the result on `this.pr`.
- **The ref-based PR lookup is effectively dead in production.** `findPRByRef` uses a **non-paginated** `pulls.list` (default `state=open`, ~30/page), but `Lottery.getPR` short-circuits on `this.prInfo` and `main.ts` **always** constructs `prInfo` from context, so `findPRByRef`/the `env.ref` plumbing runs only in tests. A branch whose PR falls outside the first `pulls.list` page would silently not be found — but that path never executes in the real action.
- **`action.yml` declares NO `outputs:` section, yet the action emits 7 named outputs** via `core.setOutput`: `reviewers`, `reviewer-count`, `assignment-successful`, `pr-author`, `author-group`, `existing-reviewers`, `matched-labels`. For a JavaScript action these work undeclared (only **composite** actions require declaration) — consumers can read them, but don't assume they are enumerated in `action.yml`.

## config-test CLI (`src/config-test.ts`)

- With **no path arg**, it resolves the default config to `<gitRoot>/.github/reviewer-lottery.yml` by walking up parent dirs for a `.git` directory; throws `"Not in a git repository"` if none found, and `"Configuration file not found"` if the default file is absent.
- CLI surface: positional config-path; `--runs`/`-r N` (default **1000** simulation runs); `--color`/`--no-color`; `--help`/`-h`. It also strips a leading `npx` script-name arg.
- **It simulates every scenario with an EMPTY `existingReviewers` array** (`selectReviewers(author, [], labels)`), so its distribution stats never model existing-reviewer subtraction and always assume a fresh PR.

## Testing

- Jest requires **BOTH** `moduleNameMapper` (maps `@actions/core`/`@actions/github` to their `lib/*.js` to bypass the ESM `exports` field) **AND** `transformIgnorePatterns` (to transform those ESM packages to CJS). Removing **either** breaks the suite (`jest.config.js`).
- Integration tests stub the real GitHub API with **nock** against `https://api.github.com` and mock `@actions/core` via `jest.mock`. The mock includes a chained `core.summary` (`addHeading`/`addTable`/`write`, all returning `this`) that **must be kept in sync with `ActionOutputsImpl.addSummary`** usage.
